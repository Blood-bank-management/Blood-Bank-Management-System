## 2. What was measured

- **Statement coverage**: the share of executable lines that ran at least
  once during the test suite.
- **Branch coverage**: the share of decision outcomes that were taken. Every
  `if` has two outcomes (true and false); a branch counts as covered only if
  the tests drove execution down it. Branch coverage is stricter than
  statement coverage: a line containing an `if` can be "covered" while one
  of its two outcomes was never tested.
- **Combined**: coverage.py's single figure, (covered lines + covered
  branches) / (lines + branches).

**Included**: all application code in the seven project apps and the
`bloodbank` package.

**Excluded** (see `.coveragerc`): migrations (generated by Django), test
files (`tests.py`, `tests/`, `tests_*.py`, `test_*.py`,
`performance_test.py`), `manage.py`, `settings.py`, `wsgi.py`, `asgi.py`
and `scripts/`. Test files are excluded because a test file always "covers"
itself, which would inflate the figure. An earlier measurement wrongly
included `requests/test_end_to_end.py`; that was fixed in commit `383d20b`
before this report was produced.

## 4. Main uncovered areas

Read from the `Missing` column of `coverage_report.txt` and checked
against the source. Listed from largest to smallest gap.

### 4.1 `donors/management/commands/seed_demo_data.py` — 0%

No automated test runs this command. This is the same blind spot behind
**DEFECT-04** (Test Plan §11): the command crashed on an import of a removed
model while all tests passed. It is now exercised by the regression script
(REG-06/07) and the CI workflow, but those runs are not measured for
coverage. **Recommended test:** call it with
`django.core.management.call_command("seed_demo_data")` twice and assert the
row counts in Test Plan §6.1.

### 4.2 `authentication/views.py` lines 35–51 — staff dashboard

`_staff_dashboard_context()` never runs: the home-page tests only use
non-staff users or check that anonymous users are redirected; no test opens
it as a staff user. Statement coverage for the file is 62.5%. **Recommended test:**
log in as a staff user, GET `/home/`, assert status 200 and that the
blood-group distribution is in the context.

### 4.3 `accounts/views.py` lines 38–56 — user-list search and filters

The administrator user list is tested for access control (SEC-07) but not
for its search box or its role/status filters. This is why `accounts`
branch coverage is only 47.6%. **Recommended test:** GET
`/administration/users/?q=...&role=staff&status=inactive` and assert only
the matching users are listed (covers BBMS-F-021).

### 4.4 `inventory/services.py` lines 131 and 138–148, `inventory/views.py` lines 100–112 — manual adjustment

`adjust_batch()` is tested for two of its three refusal paths (a negative
resulting balance, NFT-05, and a missing reason). The zero-delta refusal
(line 131) is never hit, and no test performs a **successful**
adjustment, so the balance update and the ADJUSTMENT ledger row are never
executed. The matching form validation in `inventory/forms.py` (lines
18–21, 45.5%) is also untested. **Recommended tests:** submit a zero adjustment and assert it is refused; adjust a batch by -1
with a reason and assert the new balance and one new ADJUSTMENT
`InventoryTransaction` row.

### 4.5 `auditlog/admin.py` lines 17, 20, 23 — read-only admin

The three `has_*_permission` methods that make the audit log read-only in
the Django admin site are never called by a test. The behaviour is
implemented (confirmed by inspection) but not test-verified, so the SRS
statement that the audit log is read-only "even for a superuser" rests on
code review, not a test. **Recommended test:** as a superuser, POST to the
admin change/delete URL for an AuditLog row and assert 403.

### 4.6 Smaller gaps

Mostly form-validation error branches and defensive checks:
`donations/forms.py` (77.8%), `donations/views.py` (75.4%), and single
lines in `models.py` `__str__` methods.

## 5. How this relates to the Test Plan

- Coverage was not a stated target in the SRS or Test Plan v2.1, so there
  is no pass/fail threshold. These figures are reported as evidence of how
  thoroughly the 115 automated tests exercise the code.
- 83.2% statement coverage means the suite executes most of the
  application. 61.1% branch coverage shows the main weakness: many `if`
  outcomes, mostly error paths and filters, are never driven by a test.
- Sections 4.2–4.5 are behaviours the Test Plan describes as working whose
  **success path** or **specific branch** has no automated test. They are
  not known defects; they are untested code. They are recorded here so they
  are not mistaken for verified behaviour.
